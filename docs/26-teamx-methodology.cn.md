# teamx 方法论：从团队定义到共享目标

> 中英双语：本文件为中文版；English version: [teamx-methodology.en.md](26-teamx-methodology.en.md)

---

## 开篇：三个臭裨将，顶个诸葛亮

> 三个臭裨将，顶个诸葛亮。
>
> *Three humble lieutenants can match one brilliant strategist.*

teamx 相信：**一个普通模型，乘以协作，可以超过一个顶尖模型单打独斗。**

这不是夸张。今天商业上最贵的 LLM 拥有强大的单点智能，但它仍然只是一个"人"——一次只能做一件事、只能看到自己面前的东西、没有队友可以分工、没有评审可以挑错、也没有人会在它卡住时接住它。而一个团队不一样：团队成员可以并行探索不同方向，可以互相审查，可以分工负责不同的模块，可以在某个人陷入僵局时由另一个人接管。

teamx 正是为这种 **AI Native 组织** 打造的合作工具。它把多个独立的 AI 会话（在 opencode 里，每个会话由一个大模型驱动）组织成一个有分工、有目标、有节奏的团队。你可以用多个免费的 opencode LLM 组成这样的团队——通过合理的分工、协作与审查，这个"臭裨将"团队可以做到、甚至超过昂贵商业 LLM 单独能做的事。

teamx 让"用便宜的模型拼出昂贵的效果"成为可能，而这一切的起点，是一份小小的、声明式的团队定义文件：**`TEAM.md`**。

---

## 一、为什么需要 TEAM.md

### 从"临时命令"到"团队契约"

在没有 teamx 的时候，组建一个多 AI 协作的团队，靠的是一连串临时命令：创建 team、设置 goal、加入成员、批准入队、分配角色……每一步都要手工执行，团队结构只存在于记忆和聊天记录里。

teamx 把这套过程变成了一句宣言：**团队结构是声明式配置，不是一次性命令。**

在项目仓库里放一份 `.teamx/TEAM.md`，描述：

- 团队是谁（名称、背景）；
- 要往哪里走（目标）；
- 有哪些人、各自干什么（成员画像）；
- 要生产什么文档、文档如何流转（可选：文档契约）。

然后 `teamx team create` 会**自动**读取它：建队、设目标、签发邀请函、为每个成员生成专属 `AGENTS.md` 和工作目录。整个过程可复现、可审计、可交接——任何新成员看到 `TEAM.md`，就能立刻理解这个团队在做什么、谁负责什么。

### 为 AI Native 组织而生

AI Native 组织与人类组织最大的不同是：**成员可以按需增加、并行工作、且不需要 onboarding 时间**——只要给新成员一份准确的"岗位说明"，他就能立即进入角色。TEAM.md 正是这份岗位说明的来源：

- 团队级：背景和目标，让每个成员理解"为什么做"；
- 成员级：角色、分工、技能、输出，让每个成员知道"我做什么、交付什么"；
- 文档级（可选）：团队要维护哪些文档、谁负责、谁审批，让知识生产也有流程。

## 二、TEAM.md 长什么样

TEAM.md 是一份 Markdown 文件，放在 **项目根目录的 `.teamx/TEAM.md`**。它使用宽松的 Markdown 式解析：中英文字段名都可以。

一个完整的示例：

```markdown
# 企业数字化平台

## 背景
围绕团队目标构建企业数字化平台：支持任务分派、跨网络隧道、活动/成本分析。

## 目标
- 8 月底交付 v1.0：团队协作与活动分析
- 支持跨网络 reverse tunnel

## 成员
### owner
- 姓名: 企业数字化平台
- 角色: owner
- 分工: 架构设计、目标定义、代码审查
- 技能: Rust, TypeScript, 系统设计
- 输出: 架构文档、核心代码

### 小明
- 姓名: 小明
- 角色: contributor
- 分工: 前端开发、测试
- 技能: React, TypeScript
- 输出: 看板组件、测试用例

### 小红
- 姓名: 小红
- 角色: reviewer
- 分工: 代码审查、质量保障
- 技能: Rust, 代码评审
- 输出: 审查报告
```

### 各字段的含义

| 章节 | 字段 | 含义 | 中/英文别名 |
|---|---|---|---|
| `# 标题` | — | 团队名（第一个 `# ` 标题） | — |
| `## 背景` | — | 团队背景自由文本 | `背景` / `background` |
| `## 目标` | — | 目标列表（`- ` 开头），构成团队 goal | `目标` / `goals` |
| `## 成员` | `### <key>` | 一个成员画像；`key` 用作成员目录名 | — |
| | `姓名` | 显示名 | `姓名`/`名字`/`name`/`显示名` |
| | `角色` | 角色 key（owner/contributor/reviewer/…） | `角色`/`role` |
| | `分工` | 职责/角色描述 | `分工`/`职责`/`description`/`duties` |
| | `技能` | 技能列表（逗号分隔） | `技能`/`skills` |
| | `输出` | 交付物列表（逗号分隔） | `输出`/`产出`/`outputs`/`deliverables` |

### 进阶：文档契约（`## 文档` 章节，可选）

团队不只是写代码——通常还要维护需求、设计、评审报告等文档。TEAM.md 可以用 `## 文档` 章节**声明这些文档的生命周期**：它们有标题、用途、模板、谁创建、谁所有、谁审批、状态如何流转，以及变更后通知谁。

```markdown
## 文档
### 需求说明书
- 标题: 需求说明书
- 用途: 记录团队要交付什么
- 模板: 背景, 用户故事, 验收标准
- 创建者: [pm]
- 所有者: pm
- 审批者: [owner]
- 状态流: draft -> review -> approved -> done
- 变更响应:
  - on created: 通知 pm 起草
  - on approved: 通知 owner 已定稿
```

这样，文档生产不再是"想起来才写"，而是一套有 owner、有审批、有状态流转的**知识流水线**。

## 三、方法论：TEAM.md 背后的四个原则

TEAM.md 不是一份普通配置文件，它体现了 teamx 对 AI Native 协作的四个核心判断。

### 原则 1：契约优于临时命令

> 团队结构应当是声明式的、可复现的，而不是散落在命令行和聊天记录里。

临时命令解决"现在"，契约解决"以后"。TEAM.md 让团队定义成为一种可版本化的资产：它进入 Git，随仓库演进，任何时刻都可以从零重建整个团队。这也让"换一个更便宜的模型"成为可能——团队的结构不变，只是底层驱动的模型变了。

### 原则 2：人设先于执行

> 先定义"谁干什么、交付什么"，再开始干活。

teamx 采用 **shared-goal（共享目标）** 模型，而不是"把任务分解后分发给孤立 agent"的传统多智能体模型。共享目标的团队里，每个成员都是独立工作的协作者，而不是被派活的工具。TEAM.md 的成员画像（角色/分工/技能/输出）正是这种"人设"的载体：

- **角色**：成员在团队中的身份（owner 定方向，contributor 干活，reviewer 把关）；
- **分工**：具体的职责边界，避免互相踩踏或漏项；
- **技能**：成员擅长什么，便于任务分派和互相补位；
- **输出**：成员交付什么，让"完成"有明确的验收物。

### 原则 3：文档有生命周期

> 文档不是终稿快照，而是有 owner、有审批者、有状态流转的活契约。

在 AI Native 组织里，文档往往比代码更先产生（需求、设计、评审）。如果文档没有 owner 和流程，就很容易沦为"写了一版再没人管"的孤儿文档。TEAM.md 的文档契约把文档变成**声明式的状态机**：谁创建、谁审批、如何流转、变更通知谁——让知识生产本身成为一条有管理的流水线。

### 原则 4：文件是持久知识

> teamx ledger 只存协作事件；文件（TEAM.md、AGENTS.md、设计文档）才是可持续复用的知识。

`team create` 解析 TEAM.md 后，会为每个成员生成一份专属的 `AGENTS.md`（融合项目根 `AGENTS.md` + TEAM.md 中该成员的分工/技能/输出）。这样每个 AI 会话启动时，就自动"知道自己是谁、要干什么、交付什么"。知识沉淀在文件里，而不是会话的临时上下文里。

## 四、用 grill-doc 交互式创建你的 TEAM.md

手写 TEAM.md 不难，但"想清楚团队该怎么组"并不容易：需要几个成员？每个成员什么角色？分工边界在哪？要不要文档契约？文档状态流怎么设计？这些正是 **grill-doc（Design Session）** 擅长的。

grill-doc 是一个由 team owner 主导的交互式设计会话：它把你的想法展开成一棵"设计树"，一轮一轮地问清每一个决策，并给出推荐答案，最终把结论沉淀成持久文档。用 grill-doc 来设计 TEAM.md，你得到的不是一张空模板，而是**一份经过思考、有明确取舍、可以直接使用的团队契约**。

### 4.1 启动会话

在 team owner 的 opencode 会话中：

```text
/team-grill 设计我们团队的 TEAM.md --doc .teamx/TEAM.md
```

要点：

- `--doc .teamx/TEAM.md` 把设计会话的记录直接绑定到 TEAM.md 的最终落点——设计完成后，`TEAM.md` 就是产物；
- grill-doc 会先同步团队状态、确认 owner 身份，然后读取仓库里能安全发现的事实；
- 未指定 `--doc` 时，会话记录默认写在 `docs/design/<topic-slug>.md`。

### 4.2 设计树会问什么

grill-doc 会把"TEAM.md 该怎么写"拆成一组有依赖的设计问题（`DQ-*`），大致覆盖：

| 设计问题 | 对应 TEAM.md 章节 | 示例推荐 |
|---|---|---|
| 团队背景怎么描述 | `## 背景` | 一句话说明"为什么存在这个团队" |
| 目标怎么定 | `## 目标` | 3 条以内、可验证的目标 |
| 需要哪些角色 | `## 成员` | 最少配置：owner + contributor + reviewer |
| 每个角色由谁承担 | `## 成员` | 先定角色，再为角色分配成员 key |
| 分工边界如何划分 | `## 成员` 分工 | 按模块/按职责，避免重叠 |
| 每个角色交付什么 | `## 成员` 输出 | 可验收的交付物 |
| 是否需要文档契约 | `## 文档`（可选） | 有交付文档才需要；否则可跳过 |
| 文档状态流怎么设计 | `## 文档` 状态流 | draft -> review -> approved -> done |

### 4.3 每轮怎么回答

grill-doc 同一轮会一次展示全部"当前可回答"的问题（Frontier），每个问题都带 **推荐答案和理由**。你可以逐项回答，也可以直接说：

```text
全部按推荐
```

回答含糊或遗漏时，对应问题保持未解决，不会自动采用推荐答案。回答完一轮，设计树会重新计算，下一轮出现依赖当前答案的问题。

### 4.4 需要调查的事实

如果某个问题缺事实（例如"团队里谁擅长做架构？"），owner 可以委托成员做 Fact Request（`FR-*`），成员通过 teamx 返回 Fact Report。报告只是证据，最终决定仍由 owner 做出。

### 4.5 完成条件

只有同时满足以下条件，设计会话才完成：

1. 设计树没有未访问分支；
2. Frontier 与 Remaining Branches 均为空；
3. 每个已提出的问题都有明确处理结果；
4. 设计记录与 TEAM.md 一致；
5. human owner 明确确认 Shared Understanding。

例如：

```text
我确认 Shared Understanding，可以结束设计会话。
```

完成后，`.teamx/TEAM.md` 就是一份经过完整思考的团队契约，可以直接交给 `teamx team create`。

> **推荐流程**：先跑一次 grill-doc 设计 TEAM.md，再执行 `teamx team create`。想清楚再开工，比边干边想更省时间。

## 五、从 TEAM.md 到运行中的团队

当 `.teamx/TEAM.md` 存在时，`teamx team create` 会自动完成整个 bootstrap：

```text
teamx team create 你的团队名 --session <session-key>
```

它会：

1. **解析 TEAM.md**，取团队名、背景、目标、成员画像（及可选的文档契约）；
2. **创建 team**：设置 goal（背景 + 目标）；
3. **启动 serve**：网络模式下启动内置 `teamx serve`；
4. **为每个成员签发邀请函**（invitation letter，含成员角色与专属证书）；
5. **为每个成员生成专属 `AGENTS.md`**（融合项目根 AGENTS.md + TEAM.md 中该成员的分工/技能/输出）；
6. **创建成员工作目录** `.teamx/members/[member-name]/`。

邀请函分发给成员后，他们 import 入队、owner 批准，团队即开始协作。整个过程中，`TEAM.md` 是唯一需要你维护的团队定义——它是团队的"宪法"。

## 六、常见问题

**TEAM.md 放在哪里？**
项目根目录的 `.teamx/TEAM.md`。它是 `team create` 检测的默认位置。

**团队成员变化了怎么办？**
直接编辑 `TEAM.md` 中的 `## 成员` 章节，然后重新运行相关初始化命令；`TEAM.md` 是声明式配置，改它就是改团队结构。

**文档契约是必须的吗？**
不是。`## 文档` 章节是可选的。如果团队主要靠代码和协作事件推进，可以不声明文档契约；一旦需要维护需求/设计/评审文档，再补上即可。

**中英文都能写吗？**
可以。TEAM.md 解析对中英文字段名都支持（`姓名`/`name`、`角色`/`role`、`分工`/`description`、`技能`/`skills`、`输出`/`outputs` 等），方便不同语言背景的团队。

**必须用 grill-doc 才能创建 TEAM.md 吗？**
不是。你可以直接手写，或用任意编辑器生成。grill-doc 的价值在于帮你**想清楚**——尤其是角色划分、分工边界、文档流程这类需要权衡的设计决策。

**TEAM.md 与 AGENTS.md 的关系？**
TEAM.md 是团队级契约；`team create` 会为每个成员生成一份专属 `AGENTS.md`，它是"团队契约 + 个人岗位说明"的融合，让每个 AI 会话知道自己是谁、干什么、交付什么。

## 结语

回到开篇：三个臭裨将，顶个诸葛亮。

teamx 让你有能力把一个"由普通 LLM 驱动的 AI 团队"组织起来——通过 TEAM.md 明确团队契约，通过 shared-goal 共享目标，通过角色分工与互相审查放大每个成员的能力。当你的团队由多个便宜、可用的模型组成时，你获得的不是"一个中等模型"，而是一个**有分工、有审查、有流程的组织**——这常常比一个昂贵的单点智能走得更远。

而这一切，从一个交互式设计会话、一份 TEAM.md 开始。

```text
/team-grill 设计我们团队的 TEAM.md --doc .teamx/TEAM.md
```
