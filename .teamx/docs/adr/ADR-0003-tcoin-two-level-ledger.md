# ADR-0003 — TCoin 采用**两级账本**（平台记租户余额，租户记成员明细）

- 状态：accepted
- 日期：2026-09-24
- 来源：grill 设计访谈 `design/017-tcoin-grill.md`（SD-4，DQ-0001）
- 决策人：caishu（owner）

## 背景

TCoin 是"**租户**在 teamx 里的货币"，要承载资源消耗的记账。而本系统的数据天然分两侧：

- **租户侧**（每租户独立 teamx server + 独立库）：成员、席位、**LLM 消耗明细**
  （`activity` 表按成员记 tokens/model/cost）。
- **平台侧**（平台库）：用户、**租户归属**、配额、跨租户视角。

"账本放哪"因此有三个候选：

| 选项 | 含义 | 问题 |
|---|---|---|
| (a) 平台库一处总账 | 所有 TCoin 都在平台库 | 成员级消耗明细在租户侧 → 平台要持续拉取/镜像，等于把租户数据搬进平台（与 D10"平台仅元数据"张力大） |
| (b) 每租户各记 | 币只在租户内流通 | **充值/发放只能平台做**（法币/运营额度在平台），租户侧无法自证来源；跨租户视角缺失 |
| (c) 两级 | 平台记租户余额 + 充值/发放；租户记成员明细 | 需要一条对账 |

## 决策

**选 (c) 两级账本。**

1. **平台库**（总账）：`tcoin_entries` 记**租户级**分录 —— 发放（平台→租户）、租户→成员分配、
   租户余额变动。**平台是币的唯一发行方**（v1 只发放额度）。
2. **租户 server**（分账）：记**成员级消耗明细**（按 `activity` 的 tokens×`model_pricing`
   换算为 TCoin），以及"owner 给成员分配额度"的**接收侧**记录。
3. **对账**：租户侧消耗按周期**上报/汇总**到平台总账（一条 `结算` 分录，带 `ref` 指向
   租户侧批次的摘要与行数）；平台侧可用摘要校验，不一致时**以租户侧明细为准**并留审计。

## 备选方案与为什么没选

- **(a) 平台一处总账**：要把成员级 token 明细持续镜像到平台 —— 与 design/012 D10
  （平台默认仅见元数据）冲突，且平台库成为租户数据的副本、要维护同步一致性。
- **(b) 每租户各记**：**发行方缺位** —— 币的发放/充值发生在平台（运营额度、将来的支付），
  租户侧无权凭空发币；否则任何租户都能自己印钱。

## 后果

**正面**
- 各侧只存自己**本来就有**的数据：租户侧已有 activity 明细，平台侧已有归属/用户；
  **不需要把租户数据搬到平台**。
- 币的**发行**集中在平台（可审计、可信）；**消耗**贴近数据源（实时、可自查）。
- 与 015/016 的既有方向一致：**资源归属在平台**（owner 付费）、**运行细节在租户**。

**负面 / 需接受的代价**
- **必须有一条对账**（否则两侧会漂移）：需要结算批次、摘要、校验与不一致处置规则
  （→ 由 DQ-0009 的 append-only/冲正机制承接）。
- 两处都要有账本表与写入路径（实现量翻倍），但每处都很薄（只写自己那侧）。
- 跨租户的"我的总余额"要**聚合**（平台余额 + 各租户未结算消耗），展示时要说明口径。
