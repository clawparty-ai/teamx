# ADR-0001 — 公开团队名录的数据源分层：列表不读租户，详情才读租户

- 状态：accepted
- 日期：2026-09-24
- 来源：grill 设计访谈 `design/015-teams-discovery-grill.md`（SD-9 / SD-15 / SD-24 / SD-25）
- 决策人：caishu（owner）

## 背景

云控制台要新增「全部团队」公开名录，参考 GitHub 公开项目页。团队数据天然分散：

- **可见性、团队名、namespace、归属用户** → 在**平台库**（`teams` / `tenants` / `tenant_owners`）；
- **goal、成员、任务、讨论** → 在**各自租户的 teamx server**（一个租户一个库、一套独立 CA）。

于是产生一个必须拍板的架构选择：名录（列表）从哪里取数？

## 决策

**列表与详情分层取数：**

1. **列表**（全部团队页）**不调用任何租户 server**。数据来自平台库（团队名 / 可见性 / 成员数快照 / 创建时间），必要时辅以 k8s 元数据（namespace / Deployment 存在性）。
2. **详情**（点开某个公开团队）**经 service 车道调该租户的 teamx server**，且**服务端做字段裁剪**（白名单：团队名、公开简介、goal 标题+状态、成员数、创建时间；**不含**成员名单、`invite_token`、证书与 session）。
3. **排序键受限于列表数据源**：只能用平台库可得的字段（创建时间 ↓、成员数 ↓）。不得为了"最近活跃"排序而给列表引入逐租户查询。
4. **可见性双写**：平台库是唯一事实源，k8s namespace label 是**投影**（异步、最终一致、以平台库为准自动修回）。

## 备选方案与为什么没选

| 方案 | 未选原因 |
|---|---|
| 列表逐租户实时查询（N 次 mTLS） | 第 N 次调用失败即整页失败；跨租户扇出把控制台的延迟与可用性绑定到全部租户 server；且违反 D10 的最小暴露姿态。 |
| 列表读 k8s label 为准 | 可见性是"产品语义"，应由平台库表达；k8s label 只在集群侧有消费者时才有价值（当前没有），把它当事实源会引入双源冲突。 |
| 平台库聚合全量快照（含 goal/成员名单） | 会把租户正文镜像到平台库，等于绕过 D10 的元数据边界，并引入持续同步负担。 |
| 详情也读平台库 | 详情需要租户 server 的真实状态（goal 等），平台库没有；且用户明确要求详情调租户接口。 |

## 后果

**正面**
- 列表页与租户 server 的可用性**解耦**：一个租户挂掉不影响名录。
- 单库查询即可支撑搜索/排序/分页，延迟可控。
- 守住 D10：平台不镜像租户正文，非成员只看白名单字段。

**负面 / 需要接受的代价**
- **列表不是实时活跃度**：无法提供"最近活跃"排序（除非将来在平台侧增加活跃快照，属显式新增成本）。
- 成员数是**快照**，可能与租户内真实值短暂不一致。
- 可见性双写带来**最终一致**（秒级）与补偿/对账需求（见 record SD-24）。
- 详情的字段裁剪必须在**租户 server 侧**实现（否则 `team.status` 会把 `invite_token` 等敏感字段递给非成员）——这是实现期的硬要求。
