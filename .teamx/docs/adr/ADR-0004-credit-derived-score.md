# ADR-0004 — credit 由台账事件派生评分（系统为唯一写者）

- 状态：已接受（design/018 Round 1+2，owner 全接受建议）
- 日期：2026-09-25
- 相关：design/018（credit grill）、design/015（SD-5/SD-21/SD-24）、design/016（批准即拉 Pod / 离开即释放）、
  design/017 + ADR-0003（TCoin 两级账本）、requirements/002、CONTEXT.md

## 背景

015 把 `credit` 与 `TCoin` 并列为团队的两个属性：TCoin 是货币与计量，credit 是**履约行为的信用**。
015 SD-21 已把 credit 入口预留在用户名菜单（占位），但模型一直是空白（F1：代码零命中）。

TCoin 定稿后明确了边界：**钱与信誉是两个轴** —— TCoin 回答"花了多少/欠不欠费"，
credit 要回答"**这个团队可不可信**"。同时 015 SD-5 举的典型信号"**如期支付 member TCoin**"在
**v1 不成立**，因为 TCoin v1 没有支付链（只有平台发放，017 SD-6/F3）。

credit 是一个**会被公开看**的信号（目录页），因此必须回答：谁能写、能不能刷、新团队怎么起步、
有没有后果。

## 决策

**credit = 从既有台账事件与 TCoin 余额「派生」出来的团队级评分；系统是唯一写者，无人可手改。**

具体（design/018 SD-4…SD-17）：

1. **主体**：**团队级**（v1）；成员级/用户级留 v2。
2. **派生源**（只读，不新增记账）：
   - 台账 `events`：`doc.verified` 完成数、`doc.done → verified` 转化率、`doc.rejected`、
     `blocked` 滞留、申请批准/拒绝（015 SD-24 冷却）；
   - **批准后成员实际入场率**（016「批准即拉 Pod」的可验证落点）；
   - 成员留存时长（`members.joined_at/left_at`）；
   - **TCoin 余额为负 = 欠费**（单向读 TCoin）。
3. **算法**：事件加权累计 → 映射 **0–100 分 + S/A/B/C/D 分档**；**保留构成明细**（每个事件贡献多少分）。
   **滚动 90 天 + 线性时间衰减**；全期累计仅作审计。
4. **冷启动**：基线 **60 分（B）**；有效事件 < 5 条显示「数据不足（新团队）」且**不显示分数**。
5. **可见性**：对外**公开分档徽章**；**精确分 + 构成明细只给成员/owner**。
6. **防刷**：同一 `doc`/事件去重只计一次；90 天窗口自然衰减；单团队单日正向计分封顶；
   拒绝类由 owner 决定，成员不可自刷。
7. **治理**：**无手调接口、v1 无申诉**，但提供**只读解释**（构成明细）。
8. **后果**：v1 **只展示，不影响**排序/审批/配额。

## 备选方案与否决理由

| 备选 | 否决理由 |
|---|---|
| **人工评分 / 成员互评** | 主观、易刷、涉隐私；与"公开徽章要可信"矛盾（SD-12） |
| **owner 手动加减分** | 直接破坏公信力；若未来确有线下履约，需另立"留痕+公开"的窄接口，不在 v1 |
| **独立评分表/第二套账** | 会与 events/activity 双写、可能漂移；credit 本质是**视图**，派生即可（同 ADR-0003 反对第二套口径的思路） |
| **永久累计（不衰减）** | 早期失误永久钉死、老团队吃老本；无法反映近期履约（SD-10） |
| **多维向量（不做单一分）** | 解释力更好但**公开展示**困难（徽章只能是标量/分档），v1 先标量+构成明细，向量留 v2 |
| **新团队基线 100 或 0** | 100 = 新团队与长期履约团队无差别；0 = 标签化新团队；取中位 60 + "数据不足" 保护（SD-11） |
| **v1 就用于排序/审批** | 冷启动期信号噪声大，会误伤；先建立信任再谈后果（SD-15） |

## 后果

**正面**
- 不新增记账路径：credit 是 `events`/`activity`/TCoin 余额之上的**派生视图**，无双写漂移风险。
- 唯一写者 + 公开构成 → 可解释、可审计；不依赖诚实的人工输入。
- 冷启动保护避免新团队被标签化；衰减让信用"可恢复"。

**代价 / 风险**
- **重算成本**：团队级分数需按需重算或定期物化（建议物化团队级快照到平台库，
  满足 ADR-0001「列表/目录只读平台库」；成员级明细留租户侧 —— 与 TCoin 两级结构对称）。
- **公开分档可能被误读**（B 档 ≠ 不可信）；UI 需附"数据不足/构成"的说明入口。
- **阈值/权重是拍出来的**（60 基线、<5 事件、90 天、封顶值）：需在实现后按真实数据回看，
  属于"可调参数"，调整时应记录版本，避免历史分数不可解释。
- **未来若用于排序/审批**（Remaining Branch），需重新评估防刷强度与申诉机制。

## 未决 / 后续

- 成员级/用户级 credit（v2）。
- credit 影响目录排序/加入审批（需再裁决）。
- credit ↔ 支付链：等 TCoin 有支付入口后，"如期支付"才可计量。
- 申诉通道：等 credit 产生"后果"时再设计。
